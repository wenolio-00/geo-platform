主链路与辅助部分

按时序查看 6 个关键环节，工程约束等 3 个部分单独展开。

01 · 配置品牌

Brand Config

收敛诊断对象、业务线与竞品输入。

I企业、行业、topics、competitors。
P组装并提交 Brand Config。
Obrand_config_id、entity_id。
02 · 创建任务

Diagnostic Run

创建可追踪 run。

Ibrand_config_id 与执行参数。
P创建 queued run 并启动任务。
Orun_id、status、progress。
03 · 生成 QuerySet

Questions

复用或生成 active queries。

IBrand Config 与 run 策略。
Presolve / generate queryset。
Oactive queries 与 lineage。
04 · 执行巡检

Inspection

按 query × platform 执行巡检。

Iactive queries 与 platforms。
P写入 results、message、progress。
Oinspection results。
05 · 聚合报告

report_data_v1

聚合为统一报告契约。

Iinspection results、run metadata。
P聚合指标并补齐 lineage / audit。
Oreport_data_v1。
06 · 沉淀并消费结果

Snapshot / Report

投影 snapshot 并消费报告。

Irun_id 与 report_data_v1。
P持久化 snapshot，读取并适配报告。
ODashboard、报告页、HTML 导出。
  • 主链路固定为 4 个接口：POST /brand-configs → POST /diagnostic-runs → GET /diagnostic-runs/{run_id} → GET /diagnostic-report?run_id=...。
  • 诊断报告只读真实 /api/v1/geo/*。
  • 报告页按 run_id 读取；Dashboard / history / overview 读取 completed run 派生的 snapshot。
  • 平台范围由请求中的 platforms 决定。
  1. 先确认 src/App.jsx 中 /brand/config 与 /report/diagnostic 路由边界清晰。
  2. 再确认 src/api/geo.js 已覆盖品牌配置、创建任务、轮询任务、读取报告 4 个主接口。
  3. 联调后端时，优先验证 backend/router/geo.py 的 4 个主入口与返回结构。
  4. 任务卡住或状态异常时，先查 backend/service/inspector.py 的 run 生命周期与 progress 推进。
  5. 报告或看板异常时，优先检查 backend/service/aggregator.py、src/lib/reportDataAdapter.js 与 backend/service/dashboard_snapshots.py。
  • Happy path 应依次拿到 brand_config_id、run_id、completed 状态与最终 report_data_v1。
  • Run 状态集合以当前实现为准：queued、running、aggregating、completed、failed；服务重启时还可能出现 interrupted。
  • 巡检结果必须先回写 inspection results，再聚合并沉淀 dashboard snapshot，链路才算真正闭合。
  • 字段显示异常先查 src/lib/reportDataAdapter.js，再核对 backend/service/aggregator.py 输出是否满足 schema。
  • 内容生成、effect_delta 与发布归因不属于本页主链路；需要时应单独建扩展流程图。
