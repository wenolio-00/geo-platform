GEO 工程业务链路技术设计图

这版用于给技术同事快速对齐链路边界：系统先跑诊断，并通过问题规则矩阵生成问题集，再基于报告上下文生成优化内容，最后通过手动复检做前后归因。页面同时标出哪些逻辑写在代码里、哪些来自用户配置、哪些属于运营或系统侧配置。

3分三段讲清楚：先查问题，再改内容，再看有没有变好
输入-处理-输出每段都拆成“输入了什么、系统做了什么、最后产出了什么”
研发保留接口、字段、存储和关键代码定位点，便于技术评审和排查

主链路泳道图

诊断报告 内容优化 手动复检

一、诊断报告

先把“要观察哪个品牌、看哪些问题、去哪些平台看”这些信息准备好，然后系统跑一次诊断，最后给出一份报告。

输入先准备什么
  • 品牌配置brand_config_id / BrandConfigCreate就是先告诉系统：我们要看哪个品牌、有哪些别名、盯哪些主题、对比哪些竞品。
  • 诊断任务参数queryset_policy / inspection_mode / platforms就是告诉系统：这次要不要复用老题目、用什么巡检模式、去哪些 AI 平台看。
  • 生成约束generation_constraints就是控制这次要生成多少题、至少留多少条可用题目，是否允许只跑一个小样本。
处理系统中间做什么
  • 先建一个诊断任务geo.py:post_diagnostic_run → inspector.py:create_run系统先把这次任务登记下来，拿到 run_id，然后放到后台慢慢跑。
  • 套用问题规则矩阵生成候选题rule_matrix.py → queryset.py:generate_queryset问题规则矩阵会提供题目模板、矩阵格、阶段和权重分配，是“这批题从哪里来”的关键一环。
  • 准备本次要问的问题inspector.py:resolve_queryset / queryset.py:generate_queryset如果老题目还能用，就复用；不行就按问题规则矩阵重新生成一批题，再过滤掉不合格的。
  • 去平台上实际问一遍，再汇总_inspect_queries → aggregate_report系统会把这些题发到不同平台，拿回回答，解析有没有提到品牌、引用了哪些来源，最后拼成报告。
输出最后拿到什么
  • 诊断报告数据report_data_v1 / report_data这是前端页面、HTML 导出、后面做内容优化都会用到的主结果。
  • 巡检原始结果inspection_results.json这里能看到每道题、每个平台原始回了什么，适合排查为什么结果会这样。
  • 看板快照brand_dashboard_snapshots.json可以理解成“把报告里的核心信息再整理一份”，方便后面的看板和内容优化直接取用。

二、内容优化

系统不是凭空写内容，而是先读懂上一段诊断结论，再按动作、规则和模板，生成一版可继续编辑的内容草稿。

输入先拿什么来生成
  • 诊断上下文get_dashboard_contract()这里面有最新报告、关键指标、建议动作、规则等，是写优化内容的背景材料。
  • 要执行哪个优化动作action_id / rule_id系统要先知道：这次想解决哪个问题、套用哪条规则、目标是什么。
  • 内容模板content_templates.py:template_context相当于给内容一个写法框架，帮助系统决定用什么结构来组织输出。
处理系统中间做什么
  • 先把要用的背景信息拼好get_content_generation_context把诊断结论、问题集摘要、历史版本、规则和模板都整理好，供内容生成使用。
  • 生成一版优化草稿generate_optimized_draft_async系统会检查 action、rule、template 都对不对，然后真正去生成正文。
  • 把这版草稿存下来_persist_content_version系统会记住这版内容是谁生成的、对应哪次诊断、属于哪个版本，方便后面继续追踪。
输出最后拿到什么
  • 内容版本content_versions.json / content_version_id可以把它理解为“这次优化内容的正式存档记录”。
  • 用户反馈content_feedback.json / feedback_summary如果用户觉得这版内容好用或不好用，系统会把反馈记下来。
  • 归因占位记录effect_attribution.status = awaiting_retest先占个位置，等后面跑完复检，才能知道这次改内容到底有没有带来效果变化。

三、手动复检

复检的本质很简单：不是新造一套系统，而是用户再跑一次诊断，然后把“改之前”和“改之后”的结果放在一起比。

输入比较前要拿什么
  • 基线诊断任务baseline_run_id就是“改内容之前”的那次报告，后面所有变化都拿它做参照。
  • 新的复检任务参数queryset_policy / queryset_change_reason就是告诉系统：这次复检还用不用老题目，以及为什么要复检。
  • 内容版本content_version_id这样系统才知道，这次复检是在验证哪一版优化内容。
处理系统中间做什么
  • 先重新跑一遍诊断POST /diagnostic-runs用户手动点一次复检，本质上就是重新创建一个新的诊断 run。
  • 找到可以拿来对比的那次新结果_latest_comparison_run_id如果用户没手动指定比较对象，系统就自动找“基线之后最近完成的一次”。
  • 计算前后差了多少compute_content_effect_attribution → _effect_delta / _comparability系统会对比前后指标，还会判断这两次是不是足够可比。
输出最后看到什么
  • 复检后的新报告comparison_run_id / report_data就是“改完之后”的最新表现。
  • 效果变化effect_delta能看出曝光、排名、情绪分、推荐分这些指标是变好了还是变差了。
  • 这次对比靠不靠谱comparability.same_queryset / confidence会告诉你：这两次是不是拿同一批题做的比较，结论是否足够可信。
先跑诊断，拿到问题、指标和建议 → 再基于这些结果生成一版优化内容 → 最后手动再跑一次，看改完有没有真的变好

哪些是写死的，哪些可配置

先分清楚“系统规则”“运营维护”“用户输入”和“跑完才生成”的边界

代码 / 页面写死

  • 这张图的结构和文案engineering_business_flow_design_tech_share.html三段式链路、页面样式、接口清单和存储文件名，都是当前静态说明页里固定写出来的。
  • 问题规则矩阵和问题集默认规则rule_matrix.py / queryset.py题目模板、矩阵格权重、默认候选题 40、有效题至少 30、最多 3 次尝试，当前主要由代码控制。
  • 质量过滤和内容底座queryset_policy.py / CONTENT_TEMPLATES / baseline_rules_storeQF 过滤规则、内容模板清单和基准规则，是系统默认能力，不是用户每次提交时临时写的。

用户自定义配置

  • 品牌配置BrandConfigCreate / brand_config品牌名、别名、自有域名、行业、主题和竞品，来自用户或 API 请求。
  • 诊断任务选择DiagnosticRunCreate用户可以选择平台、巡检模式、问题集复用策略，以及 generation_constraints 里的题量约束。
  • 内容生成和反馈选择template_id / feedback用户可以选择当前上下文里可用的动作、规则、模板，并对生成内容给出“有帮助 / 没帮助”反馈。

运营 / 系统侧配置

  • 平台和规则池platform_rules_store / active_rules_store平台规则、激活规则、基准规则和规则评估策略，属于系统或运营侧维护的治理资产。
  • 模板库和平台能力CONTENT_TEMPLATES / platform_registry.py内容模板、平台列表、平台提示和规则匹配方式，当前在代码里，产品语义上更接近运营配置。
  • 运行阈值MIN_ACTIVE_QUERIES / QUERYSET_CANDIDATE_QUERIES部分默认阈值可通过环境变量或运行约束覆盖，但生产门槛仍由系统保护。

运行期产物

  • 任务和问题集run_id / queryset_id诊断启动后才会生成具体任务、问题集版本和本次真正参与巡检的有效问题。
  • 报告和快照report_data / inspection_results.json / brand_dashboard_snapshots.json平台原始回答、聚合报告、看板快照都是跑完诊断后的结果，不是用户手填配置。
  • 内容版本和效果归因content_versions.json / feedback_summary / effect_attribution内容草稿、反馈汇总和复检效果变化，都是围绕具体内容版本和前后诊断结果生成的记录。

关键数据资产与存储（大白话版）

可以把这些理解成整个流程里的“账本”和“档案袋”

品牌配置

brand_configs.json
这是最前面的底稿，告诉系统“我们到底在看谁、看哪些方向、拿谁做对比”。

诊断任务

diagnostic_runs.json
这是每次诊断的总账本，记录任务状态、最后报告和失败信息。

问题集资产

querysets.json
这里放的是“这次到底问了哪些题”；有效题是真正参与巡检的题，候选题是生成出来的全集。

巡检结果

inspection_results.json
这里能看到每个平台原话怎么回答，非常适合定位问题。

看板快照

brand_dashboard_snapshots.json
可以理解为“报告的精简可复用版本”，后面很多页面和功能都直接读它。

内容版本

content_versions.json
每生成一版内容，就在这里留一份版本记录，方便回看和继续编辑。

内容反馈

content_feedback.json
记录用户觉得这版内容“好用还是不好用”。

效果归因

effect_attribution.json
这里保存“改前 vs 改后”的比较结果，是判断优化有没有效果的关键记录。

关键接口清单（更好懂版）

把接口理解成“每一步要敲哪扇门”
在哪一步 要做什么 接口 / 函数 这一步干完有什么用
诊断报告 先建品牌配置 POST /api/v1/geo/brand-configs 拿到 brand_config_id，后面诊断任务要靠它知道“在看谁”。
诊断报告 启动一次诊断 POST /api/v1/geo/diagnostic-runs 拿到 run_id，后台开始真正跑题目、问平台、出报告。
诊断报告 看任务跑到哪了 GET /api/v1/geo/diagnostic-runs/{run_id} 能知道任务还在排队、正在跑、已经完成，还是失败了。
诊断报告 把报告结果拿回来 GET /api/v1/geo/diagnostic-report?run_id=... 拿到完整报告数据，页面展示、导出和后续优化都用它。
内容优化 先拿生成内容要用的背景信息 GET /dashboard-contract + get_content_generation_context 告诉内容生成模块：现在问题是什么、该往哪个方向改。
内容优化 生成一版优化内容 POST /api/v1/geo/content/generate 会产出一个新的内容版本，同时把后面做归因要用的记录先建好。
手动复检 比较改前改后 POST /content/versions/{id}/effect-attribution 把基线任务和复检任务放在一起，算出这次优化到底有没有带来变化。

如果出问题，优先怎么排

先看哪本账，再看哪条记录

诊断报告没出来

  • 先看 diagnostic_runs.json，确认这次任务现在是什么状态。
  • 如果是问题集出问题，就继续看 last_queryset_quality_report 和多次生成尝试报告。
  • 如果是平台巡检出问题，就看 inspection_results.json 和质量门禁。

内容优化页面拿不到上下文

  • 先确认前面有没有一份真正完成的诊断报告。
  • 再确认这份报告有没有成功同步成看板快照。
  • 最后确认 action_id、rule_id 在当前上下文里是不是真的存在。

复检后还算不出归因

  • 如果还是 awaiting_retest，通常说明“改后”的那次 run 还没真正完成。
  • 如果想让前后对比更靠谱，优先复用老问题集，而不是重新换一批题。
  • 最终要看的是 effect_delta 和 comparability.confidence。
